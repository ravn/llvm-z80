# #180 peephole-audit drill — 2026-05-30

First instrumented drill on the #180 tracker (Z80LateOptimization.cpp peephole
audit; the audit `tasks/late-opt-audit-2026-05-02.md` classified 16 of 38
peepholes as "Migrate" / ~2300 LOC of stand-in code).  Goal: pick one and
decide whether it is actually movable upstream.

## The movability criterion

A peephole can move to a GISel combiner or an ISel TableGen pattern **only if it
does not depend on post-RA information** — final physical-register assignment,
physreg liveness, or FLAGS liveness.  Combiners and ISel run pre-RA, where that
information does not yet exist.

## #7 `LD A,#0 → XOR A` — MISCLASSIFIED, should be "Keep"

Current code (Z80LateOptimization.cpp:953) gates the rewrite on
`isRegDeadAfter(After, MBB, TRI, Z80::FLAGS)`: `XOR A` clears A *and* sets FLAGS
(Z=1,…), while `LD A,#0` leaves FLAGS untouched, so the 1-byte form is legal
only when FLAGS is dead at that point.  FLAGS liveness is a **post-RA** fact, so
this peephole cannot be expressed as a pre-RA combiner/ISel pattern.  The audit's
"GISel combiner / ISel pattern" home for #7 is wrong; it is a legitimate
post-RA, Z80-flag-semantics peephole → reclassify **Keep**.

(Contrast #6 `XOR #0xFF → CPL`, already RETIRED/migrated to ISel: there the
flags-dead form is emitted directly at ISel, and a flags-LIVE XOR_n 0xFF simply
never reaches post-RA — no post-RA liveness needed.  That is why #6 moved and #7
cannot.)

## Quantified post-RA coupling

Across the 6349-line pass: **51** liveness queries, **28** FLAGS-dead-gated
sites, **446** physical-register-opcode references.  The pass is intrinsically
post-RA.  Any "migrate" candidate whose validity rests on a FLAGS-dead or
physreg-dead guard is in the same boat as #7 and is *not* movable.

## Implication for the upstream-submission gate

The "16 migrate / ~2300 LOC stand-in" figure is likely **overstated**.  Several
of the 16 are post-RA-liveness-gated (like #7) and are correctly "Keep" — they
encode Z80 flag/register semantics the generic pre-RA layers cannot express,
not deficiencies in upstream infrastructure.  This *improves* the submission
story: the backend carries fewer true stand-ins than the raw count suggests.
