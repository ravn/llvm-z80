## Movability criterion

A peephole can move to a GISel combiner or ISel TableGen pattern **only if it
does not depend on post-RA information** — final physreg assignment, physreg
liveness, or FLAGS liveness.  Combiners and ISel run pre-RA, where that
information does not exist.

## Conclusion

The "16 migrate / ~2300 LOC stand-in" headline is **substantially overstated**:
- 7 already removed/migrated;
- ~5 of the remainder are post-RA-liveness/regalloc-gated and correctly **Keep**
  (they encode Z80 flag/register semantics the pre-RA layers cannot express —
  #13's comment already self-corrected to Keep);
- only **~3–5** are genuine pure-pattern combiner/ISel candidates.

The file grew 6234 → 6349 LOC since the audit *despite* the 7 removals, because
new legitimately-Z80-ISA peepholes were added (i16 EQ/NE via SBC HL, SM83 HL+/
HL- post-inc loads, SET/RES n,(HL), etc.) — these are "Keep", not stand-ins.

**Net for the upstream-submission gate (#180): the stand-in concern is largely
resolved already.** Realistic remaining migrate work is ~3–5 pure-pattern
peepholes (~600 LOC), each a focused combiner/ISel + MIR-test session mirroring
the #6 CPL migration — not the ~2300 LOC / 6–10 sessions the tracker implies.

## Finding 3 — the "genuine" candidates are pre-RA-infra builds, not ports

Inspecting the still-present candidates shows even the "migrate" ones are
post-RA-*shaped* pattern-matchers, and each is empirically load-bearing:

- **#8** `LD A,(HL); LD r,A → LD r,(HL)` is gated on `isRegDeadAfter(A)`
  (post-RA).  Migrating it means making ISel load directly into the destination
  GR8 (a load-into-GR8 pseudo expanded post-RA to `LD <phys>,(HL)`) — i.e. the
  SAME shape as the 2026-05-30 #27 indexed-addr feature, a multi-hour build, not
  a port.  Comment: disabling grows AES +18 B → LIVE, Keep until replaced.
- **#10** `LD rr,nn; INC → LD rr,nn±1` has no liveness guard (pure const fold),
  but the open question is *why* `LD+INC` survives ISel (GISel const-fold / #46
  GV+const gap).  Comment: disabling grows cpnos PROM1 +4 B → LIVE.
- **#13** truncate-fusion is `H`/`L`-dead gated; its own comment already says
  Keep.

So a migration is "build the pre-RA combiner/ISel/pseudo that makes the pattern
not arise, verify it, then delete the peephole" — exactly the #6 CPL model and
the #27 indexed-addr model.  That matches the tracker's own estimate (gated on
#177 TTI / #178 SSA pseudos / #179 combiner; ~1 session each).

## Net / next step

The #180 *stand-in* alarm is much smaller than the tracker's headline: 7/16
already gone, ~5 are correctly Keep (post-RA semantics), and the ~3–5 "genuine"
ones are each a focused pre-RA feature build (like #27/#6), not a quick port —
and the peepholes are load-bearing until replaced, so none can simply be
deleted.  Actionable next: reclassify the post-RA-gated entries to Keep in the
audit table, then schedule the genuine migrations (#8 load-into-GR8 first, it
reuses the #27 pseudo+expansion pattern) as individual sessions.
